RAG = Retrieval + Augmented + Generation
Step 1

Retrieval

질문과 관련된 문서·청크를 Vector Store에서 검색한다. 정답이 포함됐을 가능성이 높은 후보를 찾는 단계이며, 그 자체로 정답을 생성하지는 않는다.

+
Step 2

Augmented

검색된 청크를 문맥(Context)으로 구성해 LLM 입력 프롬프트에 결합한다. 이 단계에서 "무엇을 근거로 답할지"가 결정된다.

+
Step 3

Generation

구성된 문맥을 근거로 LLM이 최종 답변을 생성한다. 문맥에 없는 내용을 답하면 Grounding 실패로 분류한다.

RAG 적용 ≠ 할루시네이션 완전 제거 검색된 문서가 잘못됐거나, 정답 문서가 검색되지 않았거나, LLM이 문서를 잘못 해석하면 RAG에서도 잘못된 답변이 생성될 수 있다. RAG 적용 = 외부 근거 제공 + 출처 추적 가능 + 할루시네이션 위험 감소, 그 이상도 이하도 아니다.
사전 처리 (Pre-processing)

문서 읽기 → 텍스트 추출 → 청킹 → 메타데이터 추가 → 임베딩 생성 → Vector Store 저장

런타임 (Runtime)

질문 → 질문 임베딩 → 관련 문서 검색 → 검색 문맥 구성 → LLM 답변 생성

문서 전체를 LLM에 넣지 않는 이유

긴 문서를 질문마다 통째로 전달하면 입력 토큰 한도 초과, 토큰 비용 증가, 응답 시간 증가, 질문과 무관한 내용 포함, 긴 문서 중간 내용 누락, 답변 근거 추적 어려움이 발생한다. RAG는 문서 전체가 아니라 질문과 관련된 일부 청크만 LLM에 전달한다.

청킹 · 오버랩 · 임베딩
청킹(Chunking)

긴 문서를 검색 가능한 작은 단위로 분할하는 작업. 좋은 청크는 단독으로 읽어도 의미가 통해야 하며, 제목·본문 분리, 코드·설명 분리, 표·해설 분리가 없어야 한다.

오버랩(Overlap)

인접 청크가 일부 내용을 공유하도록 분할해 경계에서 문맥이 끊기는 문제를 완화한다. 너무 크면 중복 검색·비용 증가·문맥 중복이 발생한다.

임베딩(Embedding)

텍스트를 숫자 벡터로 변환하는 작업. 의미가 비슷한 텍스트는 벡터 공간에서 가까운 위치에 놓일 가능성이 높다. 답변 생성 기술이 아니라 검색 준비 작업이다.

벡터 검색(Vector Search)

문서 청크와 질문을 같은 임베딩 모델로 벡터화해 유사도를 비교한다. 정답이 포함됐을 가능성이 높은 후보를 찾는 것이지, 정답 자체를 생성하지 않는다.

Top-K와 유사도 임계값
Top-K

유사도가 높은 문서를 몇 개 가져올지 정하는 값. 너무 작으면 정답을 놓치고, 너무 크면 관련성 낮은 문서와 중복이 함께 전달된다. 고정된 정답은 없으며 평가 질문을 실행해 적정값을 결정한다.

Similarity Threshold

일정 유사도보다 낮은 문서를 제외하는 기준. Top-K와 결합되어 "최대 K개 검색 + 임계값 미만 제외"로 동작한다.

검색 방식 4가지
① 키워드 검색

정확한 단어·문자열 매칭에 유리. 클래스명, 에러 코드, 버전, API 경로 등 고유 식별자 검색에 적합하다.

② 벡터 검색

단어가 일치하지 않아도 의미가 비슷한 문서를 찾는 데 유리. 표현이 달라도 의미 유사성으로 검색될 수 있다.

③ 하이브리드 검색

키워드 검색과 벡터 검색을 함께 사용하고, RRF(Reciprocal Rank Fusion)로 순위를 결합한다: Score = Σ 1/(k+rank)

④ 리랭킹(Reranking)

1차 검색 후보를 더 정밀하게 재평가해 최종 순서를 조정. 문서가 적고 결과가 안정적이면 반드시 필요하지는 않다.

검색 · 생성 품질 지표
Hit@K = 정답 청크가 상위 K개 안에 포함된 질문의 비율 Recall@K = 검색된 정답 청크 수 / 필요한 전체 정답 청크 수 Precision@K = 검색된 정답 청크 수 / 실제 검색 결과 수 MRR = Σ(1 / 첫 정답 청크 순위) / 답변 가능한 질문 수

답이 없는 질문(unanswerable)은 이 네 지표 계산에서 제외한다.

Retrieval 실패 vs Generation 실패

검색 결과를 먼저 확인한 뒤 생성 실패 유형을 판정한다. 정답 청크가 검색되지 않은 질문은 Generation 실패로 분류하지 않는다. 이 구분이 이 학습 전체에서 가장 중요한 원칙이다.

검색 결과생성 결과분류

정답 청크 없음오답RETRIEVAL_FAILURE
정답 청크 있음오답GENERATION_FAILURE
정답 청크 없음정답처럼 보임사전 학습 지식 사용 가능성
관련 문서 없음답변 거부정상 거부

GraphDB ≠ Graph 기반 RAG ≠ Microsoft GraphRAG
GraphDB

노드와 관계를 저장하고 탐색하는 데이터베이스 그 자체 (예: Neo4j)

Graph 기반 RAG

그래프 탐색 결과를 RAG 문맥 구성에 사용하는 구조. 관계 탐색으로 관련 문서를 찾고, 최종 답변 근거는 원문 청크에서 확인한다.

Microsoft GraphRAG

엔티티·관계 자동 추출, 커뮤니티 탐지, 커뮤니티 요약까지 포함하는 별도의 파이프라인. 이 학습에서는 포함하지 않는다.

주의

Neo4j에 임베딩을 저장하고 벡터 검색만 수행하는 것은 GraphRAG가 아니다.

실제 실행 사례
  • 정상 사례 — "그래프 신경망에서 이웃 정보를 집계할 때 어떤 함수를 사용해야 하는가?" → 정답 청크 검색 성공, "순서 불변 집계 함수(평균·합·최댓값)를 사용해야 한다"는 근거 있는 답변 생성.
  • 실패 사례 — "이 책을 쓴 사람은 누구인가?" (Top-K 5, Threshold 0.7 → 검색 결과 0건) 수동 RAG는 정상 거부했지만, Advisor는 검색 문서 근거 없이 답변을 생성해 Grounding 실패 + 사전 학습 지식 사용 가능성으로 분류됨.

04 전체 학습을 통해 이해한 것

검색 실패는 한 지점의 문제가 아니다

7개 Phase를 통과하며 반복적으로 확인된, 재사용 가능한 원칙 6가지.

01

구조 이해

청킹·임베딩·벡터검색·생성은 서로 다른 처리 단계이며, 문제가 생기면 어느 단계인지 먼저 구분해야 한다.

02

Retrieval vs Generation

정답 청크가 검색되지 않은 질문은 답변이 틀렸더라도 Generation 실패로 분류하지 않는다.

03

개선이 항상 성공은 아니다

하이브리드·RRF·리랭킹을 적용해도 후보 생성 단계 자체가 실패하면 품질은 개선되지 않는다.

04

측정 없이는 판단하지 않는다

Hit@K, Recall@K, Precision@K, MRR로 개선 전후를 수치로 비교해야 한다.

05

GraphDB의 역할

GraphDB는 관계와 문서 식별자만 저장하고, 최종 답변 근거는 항상 원문 청크에서 확인한다.

06

실패도 유효한 결과

측정하지 않은 값은 임의로 채우지 않고, 실패 원인과 함께 있는 그대로 기록한다.
